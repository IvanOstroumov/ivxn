Компиляция — одна из более измеримых, чувствительных к железу задач разработчика — вот что реально двигает цифру.

## Ранжировано по реальному влиянию

<Callout>
Для большинства современных, хорошо распараллеленных систем сборки количество ядер обычно имеет наибольшее влияние на время компиляции, за которым следует ОЗУ (избегание свопа) и скорость хранилища (обработка множества промежуточных файлов). Чистая тактовая частота одного ядра важна, но обычно меньше, чем эти три фактора, для больших многофайловых сборок.
</Callout>

1. **Количество ядер**, для тулчейнов, которые параллелизуют компиляцию по файлам (большинство современных так и делают, часто по умолчанию). Больше ядер напрямую сокращает время настенных часов компиляции для больших проектов с множеством независимо компилируемых файлов.
2. **Объём ОЗУ**, чтобы избежать отката системы к медленному свопу на основе диска в середине сборки — см. наше [руководство по ОЗУ](/blog/how-ram-works-simply) о том, почему этот откат так дорог. Большие проекты с множеством параллельных задач компиляции могут использовать больше ОЗУ, чем ожидается.
3. **Скорость хранилища**, поскольку большая сборка читает и записывает множество промежуточных файлов — см. наше [сравнение NVMe и SATA](/blog/nvme-vs-sata-ssd-real-difference) о том, насколько это реально важно по сравнению с разницей в спецификациях, которую вы бы не почувствовали в другом месте.
4. **Тактовая частота одного ядра**, которая важна для частей сборки, которые нельзя распараллелить (некоторые этапы линковки, некоторые однопоточные этапы тулчейна) — реальный фактор, но обычно меньший, чем вышеперечисленное, для типичных больших многофайловых проектов.

## Практическая форма рекомендации по сборке

| Приоритет | Обоснование |
|---|---|
| Процессор с большим количеством ядер | Напрямую сокращает время параллельной сборки |
| Достаточно ОЗУ, чтобы избежать свопа при пиковом использовании вашей реальной сборки | Избегание медленного отката к свопу важнее, чем люди ожидают |
| Быстрое NVMe-хранилище | Сокращает время на ввод-вывод промежуточных файлов |
| Приличная скорость одного ядра | Помогает нераспараллеливаемым частям, но вторичный приоритет |

## Проверьте ваш конкретный тулчейн, прежде чем предполагать

Не каждая система сборки параллелизуется одинаково хорошо — некоторые языки/тулчейны исторически имели больше последовательных узких мест (определённые этапы линковки, однопоточные этапы), чем другие. Прежде чем сильно оптимизировать под количество ядер, проверьте, действительно ли сборка вашего конкретного проекта хорошо использует несколько ядер (видно в мониторинге системных ресурсов во время реальной сборки) — оптимизация под параллельное количество ядер, когда ваша сборка на самом деле плохо параллелизуется, тратит впустую бюджет, который мог бы пойти на ОЗУ или хранилище.

Для чистой пропускной способности многоядерной компиляции при данной цене это часто благоприятствует тому чипу, который предлагает больше ядер за деньги в данном поколении — см. наше более широкое [сравнение Intel против AMD Ryzen](/blog/intel-vs-amd-ryzen-2026) для специфики текущего поколения, поскольку это меняется по циклам продуктов.
